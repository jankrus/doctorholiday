# Security traceability matrix

Issue [#47](https://github.com/jankrus/doctorholiday/issues/47). Where is each security requirement and each selected threat mitigation implemented, and how is it proven? One table links every requirement (SR) to its control, the code or configuration, the test or scan, and the evidence. A second table does the same for the threats of the three implemented STRIDE categories, and a third for the Kubernetes items of brief §4.

- **State:** 2026-11-26, `main` after the CI/CD block (runs 95 to 107). The status of each row is what the code does today. The *Status* column of [stride.md](../threat-model/stride.md) was brought up to date with this matrix, and the check script verifies that both agree for the selected threats.
- **Sources:** requirements [security-requirements.md](../architecture/security-requirements.md) (SR-01 to SR-11), threats [stride.md](../threat-model/stride.md) and the selection in [stride-selection.md](../threat-model/stride-selection.md), deviations [deviations.md](deviations.md).
- **Status:** *Implemented* (control in place, verified), *Partial* (in place with the named gap), *Planned* (open issue), *Accepted* (risk accepted with a reason in the threat model).
- **Implementation and verification** name files as `path::symbol`: the file exists and contains the symbol (function, class or test name). Line numbers are avoided on purpose, they rot.
- **Evidence** is a file of the pipeline run on the branch `evidence` (`evidence/<image>/<type>/<run>-<sha>-<file>`, here run 95 with the prefix `00095-d01d074`, backend as the example; the frontend has the same files) or a link to a workflow run. The evidence branch is copied into `main` before the submission (D-09, `make evidence-sync`).
- **Check:** `python3 scripts/check_traceability.py` (also `make check-traceability` and the `meta` job of the pipeline) fails if an SR has no implemented control, a file or symbol does not exist, a link or evidence path does not resolve, or a selected threat has no row.

## Known gaps

The acceptance criterion of #47 asks for an implementation and a verification per requirement. Every SR has at least one control that is implemented or partly implemented, but not every requirement is complete:

- **SR-09 (TOTP):** only the groundwork exists (C-09.1); the flow is #21, a bonus item of the brief.
- **SR-10 (audit log):** authentication events are recorded; admin operations, denials and the read endpoint are open (#20, #100).
- **SR-11 (HTTP hardening):** the API is done; the Content-Security-Policy of the frontend is #27.
- **Planned threats:** TH-11 (client IP, #75), TH-34 (TBAC, #55), TH-61 (private repository and packages, #48).
- **Verification gaps inside implemented controls:** no automated manifest check for secret values (C-05.2), no `can-i` check of ServiceAccount rights (C-08.2), no test of the append-only grant (C-10.1), no header test for the frontend (C-11.2).
